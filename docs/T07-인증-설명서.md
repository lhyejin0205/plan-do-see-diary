## 1. 무엇을 막으려 했나 (위협과 목표)

- T06 다이어리는 로그인이 없어 링크를 아는 누구나 기록을 보고 고칠 수 있었다.
- 목표: **가입한 사람마다 자기 기록만** 읽고 쓰게 한다. 로그인하지 않은 사람과 다른 계정은 화면뿐 아니라 **서버에서** 거절된다.
- 막는 대상: 로그인하지 않은 요청, 다른 계정의 기록 읽기·고치기·지우기, 다른 사람 이름(owner_id)으로 기록 넣기.

## 2. 사용한 인증 방식과 선택 이유

- **Supabase Auth, 이메일 + 비밀번호.**
- 이유: T06에서 이미 Supabase DB를 쓰고 있어서, 같은 서비스의 인증을 붙이면 로그인한 사람의 id(`auth.uid()`)를 DB 정책에서 바로 쓸 수 있다. 별도 서버 없이 정적 사이트(Vercel)로 유지된다.
- 비밀번호는 Supabase가 해시로 저장하며 앱 코드나 DB 표에 남지 않는다.
- **가입 확인 메일: 켜 둠(Supabase 기본값).** 다른 사람의 이메일로 가입해 그 주소를 차지하는 일을 막기 위해서다. 확인 링크는 T07 주소로 돌아오도록 Site URL과 Redirect URL을 `https://plan-do-see-diary-t07.vercel.app`로 설정했다.

## 6. 아직 해결하지 못한 점

**보안·운영**
- 가입 확인 메일은 Supabase 기본 메일 서버로 보내므로 시간당 보낼 수 있는 수가 적다. 여러 사람이 한꺼번에 가입하면 메일이 늦거나 막힐 수 있다.
- 비밀번호 재설정(비밀번호를 잊었을 때) 화면이 없다.
- 로그인 시도 횟수 제한은 Supabase 기본 설정에 맡기고 따로 조정하지 않았다.
- 로그인 정보(세션)는 브라우저 localStorage에 저장된다. 화면에 넣는 글자는 모두 이스케이프했지만, 콘텐츠 보안 정책(CSP) 헤더는 아직 걸지 않았다.
- T06과 같은 Supabase 프로젝트를 쓴다. T07 표는 잠갔지만, T06의 `pds_*` 표는 과제 특성상 여전히 누구나 읽고 쓸 수 있다.
- 차단 시험에 쓴 두 계정이 실제 내 이메일이고 비밀번호가 같다. 계속 쓸 계정은 비밀번호를 바꾸고, 시험 전용 계정은 지워야 한다.

**확인하지 못한 것**
- 회원가입 → 확인 메일 → 링크로 돌아와 로그인하는 흐름은 실제 메일로 끝까지 확인하지 않았다. 시험 계정은 대시보드에서 확인 없이 만들었다.
- 관찰 규칙 저장은 실제 계정으로 해 보지 않았다. 규칙은 한 번 저장하면 고치거나 지울 수 없어서, 시험으로 넣으면 내 계정에 v1이 남기 때문이다. 서버가 규칙 수정을 막는 것(403)만 확인했다.

**설계상 한계**
- 관찰 규칙을 잘못 저장해도 고칠 수 없고 새 버전으로만 바로잡을 수 있다. 기록을 지키려고 일부러 그렇게 만들었지만, 오타 하나에도 버전이 늘어난다.
- 계정을 지우면 그 사람의 기록도 함께 지워진다(on delete cascade). 지우기 전에 내보내기로 받아 두어야 한다.
