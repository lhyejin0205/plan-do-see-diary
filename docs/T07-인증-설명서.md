## 1. 무엇을 막으려 했나 (위협과 목표)

- T06 다이어리는 로그인이 없어 링크를 아는 누구나 기록을 보고 고칠 수 있었다.
- 목표: **가입한 사람마다 자기 기록만** 읽고 쓰게 한다. 로그인하지 않은 사람과 다른 계정은 화면뿐 아니라 **서버에서** 거절된다.
- 막는 대상: 로그인하지 않은 요청, 다른 계정의 기록 읽기·고치기·지우기, 다른 사람 이름(owner_id)으로 기록 넣기.

## 2. 사용한 인증 방식과 선택 이유

- **Supabase Auth, 이메일 + 비밀번호.**
- 이유: T06에서 이미 Supabase DB를 쓰고 있어서, 같은 서비스의 인증을 붙이면 로그인한 사람의 id(`auth.uid()`)를 DB 정책에서 바로 쓸 수 있다. 별도 서버 없이 정적 사이트(Vercel)로 유지된다.
- 비밀번호는 Supabase가 해시로 저장하며 앱 코드나 DB 표에 남지 않는다.

## 4. 접근 차단을 확인한 기록 (성공한 요청과 거절된 요청)

테스트용 계정 A, B 두 개로 확인한다. 실제 이메일 주소는 `a@…`, `b@…`처럼 가린다.

| # | 누가 | 요청 | 기대 | 실제 결과 (채울 것) |
| --- | --- | --- | --- | --- |
| 1 | A | 자기 계획 추가 `POST /rest/v1/pds7_plans` | 201 성공 | |
| 2 | A | 자기 계획 읽기 `GET /rest/v1/pds7_plans` | 200, A의 행만 | |
| 3 | B | A 계획 id로 읽기 `GET /rest/v1/pds7_plans?id=eq.<A의 id>` | 200, 빈 배열 `[]` | |
| 4 | B | A 계획 고치기 `PATCH …?id=eq.<A의 id>` | 0행 처리, A의 행은 그대로 | |
| 5 | B | A 계획 지우기 `DELETE …?id=eq.<A의 id>` | 0행 처리, A의 행은 그대로 | |
| 6 | B | `owner_id`를 A로 넣어 추가 | 403, `new row violates row-level security policy` | |
| 7 | B | A의 계획에 Do 달기 | 거절 (트리거 또는 RLS) | |
| 8 | 로그인 없음 | `GET /rest/v1/pds7_plans` | 401/403, `permission denied` | |
| 9 | 로그인 없음 | 결과물 URL 첫 화면 | 로그인 화면만 보이고 기록 없음 | |

각 줄에는 요청(메서드·경로), 응답 코드, 응답 본문 일부를 적는다. 토큰은 `Authorization: Bearer ****`로 가린다.
